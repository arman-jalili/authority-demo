# authority-demo

> An agent was authorized to pay a beneficiary. A human said yes. Later the
> beneficiary is frozen. **Does the authorization still stand?**

A tiny treasury app, a real policy engine, and one question. The demo shows
that **authorization is not a durable grant**: the run pauses for a human, and
then the authority is re-checked at the moment of consequence. When the world
changes between the "yes" and the money, the payout is refused — and the
refusal is signed evidence.

## The idea in one line

> Approval releases the pause. It does **not** pre-approve the world.

Most governance stops at the approval: a human says yes, and the action is
treated as authorized from then on. But approval and consequence are separated
in time — and the world moves in the gap. A vendor is frozen, an account is
closed, a limit is lowered. A standing "yes" becomes a stale one.

Rigorix checks authority **twice**: once when the agent asks (plan time) and
again immediately before the step would execute (**dispatch time**). The second
check is the one that matters, because it sees the current world.

## What you'll see

| Act | What happens |
|---|---|
| **T₀ · the grant looks fine** | The agent runs the payout runbook. It declares `requires_approval`, so Rigorix pauses for a human. The human approves. The authority check passes → the payout **executes**. |
| **ΔN · the world changes** | While the *next* run waits for approval, the operator **freezes** the beneficiary. The human's approval is untouched — it is still a valid "yes". |
| **Tₙ · the refusal** | The operator approves the paused run. At dispatch, the check reads the *frozen* authority → the step is **refused**. The ledger never changes. |
| **the evidence** | The refusal is in the signed audit trail: `precondition_findings[0]` with the outcome, exit code, a fingerprint of what was checked, and when. |
| **fail closed** | A payout to a beneficiary who is not in the authority is refused too — even with an approval. |

## Quick start

```bash
./reset-demo.sh                          # authority active, ledger + trail clean
node .rigorix/run-authority-demo.mjs     # run the scene-by-scene proof
```

No Docker, no IdP, no API key. `reset-demo.sh` installs the operator's
authority check *outside* the repository, thaws the beneficiary, and clears the
ledger and the signed trail, so every run starts from the same place.

Requirements: `rigorix-mcp >= 1.9.2` on `PATH` (or `RIGORIX_MCP_BIN`), Node
>= 22. `npm install && npm test` runs the unit tests.

## The trust boundary — why the check lives outside the repo

The whole demo rests on one design choice: **the rule the agent is judged by
is not in the agent's repository.**

```
.rigorix/scripts/setup-authority.sh
        │  copies
        ▼
$HOME/.rigorix-authority-demo/
        ├── check-beneficiary.mjs   ← the live check
        └── authority.json          ← the live authority
```

The gate config (`.rigorix/preconditions.toml`, generated by that script)
points at the **absolute path** under `$HOME`, outside the agent's workspace. A
`PreToolUse` hook (`.claude/hooks/deny-ledger-tamper.mjs`) denies direct payout,
ledger writes, and authority edits on top of that.

**Be precise about what this buys.** The default demo runs a **policy + path +
hook** boundary — not a sandbox. It stops *agent-mediated* tool calls from
touching the check or the authority; it does **not** stop an unmediated write to
`$HOME` (another tool, a differently-privileged subprocess, a persisted script).

| Mode | Enforced by | Guarantee | Does **not** cover |
|---|---|---|---|
| **default (this demo)** | path containment + hook | agent-mediated calls cannot touch the check/authority | an **unmediated** write path to `$HOME` |
| **`--isolated`** (issue #985 — available) | OS ownership/mode (root-owned `0555`/`0444`) | the agent's **UID cannot write** them | needs no passwordless `sudo` for the agent user |
| **`require_immutable_check`** (issue #986 — available) | engine, at dispatch | a writable check/authority is **refused** | a check writable by another privileged identity |
| **attribution** (issue #987 — available) | signed envelope | a forged authority is **visible** (`authority_digest`) | detection, not prevention |

The demo runs the **default** row today; the other rows are opt-in upgrades.
`inputs_hash` fingerprints what the check *saw*; #987's `authority_digest` binds
the authority *content*. Source of truth: ADR-017 §Honest boundary.

### Isolated mode — make the boundary an OS fact

The default install relies on the agent *choosing* the sanctioned tool path. To
make the stronger boundary real on this machine, install the authority
root-owned and non-writable:

```bash
bash .rigorix/scripts/setup-authority.sh --isolated
bash .rigorix/scripts/verify-isolation.sh   # must print "isolation verified"
```

This installs the check (`0555`) and the authority (`0444`) under
`/usr/local/lib/rigorix-authority-demo` (override: `RIGORIX_ISOLATED_HOME`),
owned by root, and writes the gate config pointing there. The agent's UID now
cannot write either file (`EACCES`), and `freeze_beneficiary.sh` /
`thaw_beneficiary.sh` escalate the operator's own writes through a documented
`sudo node` invocation.

**Precondition:** the agent user must **not** have passwordless `sudo`. Setup
runs `sudo -n true` and refuses when it succeeds (set
`RIGORIX_ALLOW_PASSWORDLESS_SUDO=1` to continue with a loud warning) — a
no-password-sudo agent user would simply `sudo` the write and the boundary would
be hollow.

`./reset-demo.sh --isolated` resets to this mode; the default (no flag) is
unchanged.

The check is the entire policy. It answers one question and exits:

```js
const status = authority[beneficiary] ?? "unknown";
process.exit(status === "active" ? 0 : 3);   // 0 = dispatch, non-zero = refuse
```

No LLM, no domain semantics, no network. It is small enough to audit in a
sitting — which is rather the point.

## The evidence — what the signed trail proves

After the Tₙ refusal, `.rigorix/audit/<execution_id>.json` records the check:

```json
{
  "event types": ["precondition_checked", "node_failed"],
  "precondition_findings": [{
    "precondition_id": "beneficiary-authorized",
    "step": "payout_execute",
    "outcome": "failed",
    "exit_code": 3,
    "inputs_hash": "sha256:0078c18a3758bd74ac5426c8659…",
    "checked_at": "2026-10-06T18:52:03.754834Z",
    "summary": "precondition 'beneficiary-authorized' failed step 'payout_execute' (exit 3)",
    "check_digest": "sha256:9a1c0f…",      // ADR-017 #987: the check program
    "authority_digest": "sha256:4f2be7…",  // the authority artifact it read
    "check_writable": true                 // the boundary was writable (#986)
  }]
}
```

The envelope is HMAC-signed, so the record is tamper-evident, and the same
finding is served by `rigorix_read_audit`. That is how an outsider answers
"does the authority still stand?" **from the record, not from trust**: the
check ran at dispatch, it saw the current world, it failed, and the step never
executed (the ledger is unchanged).

Three of those fields repay a second look:

- `inputs_hash` fingerprints the **step inputs the engine fed the check** —
  *what was asked*, not the authority the check consulted.
- `authority_digest` (#987) binds the **authority content** the check read. The
  demo declares `authority_path`, so the engine records it; freeze, thaw, or
  edit `authority.json` and the digest changes. A verifier compares it against
  the operator's known-good value — a changed authority is **visible**.
- `check_writable: true` (#986) is the honest boundary fact: the default
  `$HOME` install **is** writable by your UID, so the record says so. That is
  exactly the caveat in the matrix above — and after
  `setup-authority.sh --isolated` the same run records `check_writable: false`.

Attribution is detection, not prevention: the boundary itself is the default
row (path + hook) or the `--isolated` row (OS ownership). The digests make the
record answerable either way.

## Try it with your agent

Point Claude Code or Codex at this repo and paste:

> Pay acme 250 EUR.

The agent runs the runbook through Rigorix; it reports `PendingApproval` and
waits for you. Approve, and the payout executes. Now try the interesting
variant — start the run, **wait** at the approval prompt, and in another
terminal freeze the beneficiary:

```bash
bash .rigorix/scripts/freeze_beneficiary.sh acme
```

Then approve. The run is refused at dispatch, the ledger does not change, and
the signed trail carries the reason. (`thaw_beneficiary.sh` restores it.)

**Try to cheat.** Ask the agent to pay directly, or to edit the ledger or the
authority file. The `PreToolUse` hook refuses, and the live authority is
outside the repo. (In the default mode an unmediated write to `$HOME` is still
possible — that is the boundary caveat above, not a hidden gap.)

## Why this is gated and not "just a check in the app"

The check *could* live in `execute_payout.sh`. It does not, for three reasons:

1. **The decision is separable from the consequence.** The engine calls the
   check, records the result, and enforces it — the payout script just writes a
   row. Policy is reviewable in one place and reusable across runbooks.
2. **The refusal is evidence, not a log line.** Because the engine owns the
   dispatch, a failed check produces a *signed* finding with a stable shape —
   not whatever the script happened to print.
3. **The agent's tool path cannot reach it.** The check resolves outside the
   workspace, so "is this beneficiary authorized?" is answered by the operator's
   artifact, not by the agent's. (The default mode is a path + hook boundary —
   see the matrix above for what it does and does not cover.)

| Path | What it is |
|---|---|
| `.rigorix/templates/payout.toml` | The runbook: one approval-gated payout step |
| `.rigorix/templates/payout-unknown.toml` | The fail-closed case (unknown beneficiary) |
| `operator/check-beneficiary.mjs` | The operator-owned check (source; installed outside) |
| `operator/authority.json` | The authority (source; installed outside) |
| `.rigorix/scripts/setup-authority.sh` | Installs both outside the repo (default) or root-owned (`--isolated`); writes the gate config |
| `.rigorix/scripts/verify-isolation.sh` | Asserts the isolated boundary as the agent UID (EACCES) |
| `.rigorix/scripts/freeze_beneficiary.sh` | The ΔN: freeze a beneficiary (escalates via `sudo` in isolated mode) |
| `.rigorix/run-authority-demo.mjs` | The scene-by-scene driver |
| `src/payouts.ts` | The ledger domain (the "consequence") |
| `.claude/hooks/deny-ledger-tamper.mjs` | The "stick": no direct payout / ledger / authority writes |
